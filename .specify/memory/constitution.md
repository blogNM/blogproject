# 메인블로그 헌법 (Constitution)

이 문서는 메인블로그 개발에서 어떤 기능을 만들든 지켜야 하는 원칙입니다. Spec Kit의 `/speckit-plan`은 계획을 세울 때 이 문서와 맞는지 확인합니다(Constitution Check). 근거는 요구사항분석서 1편 4장(비기능)·7장(구현 방식), 2편 8장(결정 기록)입니다.

## 핵심 원칙

### I. 문서가 먼저, 근거는 ID로

- 기능을 만들거나 고치기 전에 `specs/` 안의 해당 spec과 요구사항 ID(예: `USR-02`), 결정 기록(예: `D-66`)을 먼저 확인한다.
- spec, plan, tasks, 커밋 설명에는 근거가 되는 요구사항 ID와 D-번호를 적는다.
- 세부 정책에서 상태가 **보류**인 항목, spec의 `[NEEDS CLARIFICATION]` 항목은 임의로 정하지 않고 사람에게 묻는다.
- 정한 내용이 바뀌면 코드보다 문서를 먼저 고치고, 새 결정은 `docs/03-decisions/`에 D-번호로 남긴다.

**이유**: 요구사항이 81건의 결정을 거쳐 자주 바뀌었고, 이전 결정이 뒤집힌 경우(D-11 → D-53, D-63 → D-66)가 많다. 근거를 ID로 남겨야 무엇이 최신인지 추적할 수 있다.

### II. 블로그별 역할은 매 요청마다 서버가 확인한다 (양보 불가)

- 블로그장·부블로그장·멤버는 계정 종류가 아니라 블로그별 역할이다. 한 회원이 A 블로그에서는 블로그장, B 블로그에서는 멤버일 수 있다.
- 모든 요청에서 서버가 DB로 블로그별 역할과 정지·강퇴 여부를 확인한다. 토큰 내용만 믿지 않는다. 토큰에는 회원 번호 정도만 담는다 (SEC-07, D-53).
- 주소 단위로 비회원·회원·관리자를 나누고, 블로그별 역할은 `@PreAuthorize` 메서드 보안으로 확인한다 (SEC-11).
- 부블로그장은 블로그장이 체크한 권한만 갖는다 (D-71).
- 블로그장과 관리자는 남의 글을 수정할 수 없다 (D-07, D-58).

**이유**: 이 플랫폼에서 가장 중요한 보안 항목이 SEC-07이다. 권한 확인을 기능마다 직접 넣으면 하나만 빠뜨려도 구멍이 생긴다.

### III. XSS·CSRF는 정해진 한 곳에서 막는다 (양보 불가)

- 글 본문만 서버가 마크다운을 HTML로 바꾼 뒤 jsoup으로 걸러서 보낸다. 화면은 본문에만 `innerHTML`을 쓰고, 닉네임·댓글·태그 등 나머지는 모두 `textContent`로 넣는다 (SEC-06, D-64, D-66).
- 상태를 바꾸는 모든 JS 요청(POST·PUT·DELETE)에 `X-XSRF-TOKEN` 헤더를 붙인다. 공통 `api.js` 한 곳에서 처리한다 (SEC-10).
- 보안 헤더(X-Frame-Options, X-Content-Type-Options: nosniff, Content-Security-Policy, Strict-Transport-Security, Referrer-Policy)를 Spring Security로 설정한다 (SEC-12, D-09).
- 로그인 토큰은 HttpOnly·Secure 쿠키에만 담는다. localStorage에 두지 않는다 (SEC-04).

### IV. 계정과 개인정보는 드러내지 않는다

- 비밀번호는 bcrypt로만 저장한다 (SEC-01, D-81).
- 비밀번호 찾기·이메일 찾기 화면은 가입 여부와 관계없이 같은 문구를 보여준다 (D-28, USR-06). 가입 화면만 이메일 중복 확인으로 알려 주고, IP별로 횟수를 제한한다 (D-99).
- 인증번호와 임시 토큰은 DB에 해시로 저장하고, 만료·횟수 제한을 두며, 쓰거나 만료되면 바로 지운다 (USR-02, SEC-05, 4.5).
- 개인정보 가림(마스킹)은 화면이 아니라 서버가 응답을 만들 때 한다 (4.4, D-22).
- 블랙리스트는 원문 대신 해시로 보관한다 (BLG-11, 4.6).
- 관리자 조치와 개인정보 "전체 보기"는 모두 기록한다 (ADM-06, SEC-09).

### V. 서버 이중화에 대비해 상태를 서버 메모리에 두지 않는다

- 세션 외에는 서버 메모리에 상태를 두지 않는다. 인증 코드, 횟수 세기, 임시 데이터는 DB에 저장한다 (SCL-01).
- 파일 저장은 `FileStorage` 인터페이스로 분리하고 1차에는 디스크 구현만 쓴다 (SCL-02, D-75).
- 모든 `@Scheduled` 작업에는 처음부터 ShedLock을 걸고, `zone = "Asia/Seoul"`을 지정한다 (SCL-03, D-12).
- 확인 필요: 4.3 이중화 표는 IP별 요청 제한을 1차에 "서버 메모리에서 센다"고 적고 있어 SCL-01과 어긋난다. 정하기 전까지는 요청 제한 저장소를 인터페이스로 분리해 둔다 (specs/README.md "확인이 필요한 항목").

### VI. 바뀔 수 있는 숫자는 설정으로 뺀다

- 개수 제한 같은 값은 설정 파일 + 환경변수로 둔다. 예: `blog.limit.public=${BLOG_LIMIT_PUBLIC:3}` (D-68).
- 개수 제한을 확인하고 만드는 과정은 DB에서 잠가 동시 요청으로 제한을 넘지 않게 한다 (BLG-10, D-68).

### VII. 업로드는 세 겹으로 검사한다

- 허용 형식은 jpg·jpeg·png·gif·webp뿐이다. svg, 동영상, 문서, 압축 파일은 막는다.
- 확장자, MIME 타입, 파일 시그니처를 모두 검사한다 (SEC-08, 6.3).
- 서버에는 UUID 이름으로 저장하고 원래 이름은 DB에만 둔다. 업로드할 때 EXIF(GPS 등)를 지운다.

### VIII. 1차는 단순하게, 2차로 미룬 것은 미룬 채로

- 1차 범위 밖으로 정해 둔 것은 만들지 않는다: 문자(SMS) 인증, 자동완성, SNS 공유(링크 복사 외), 썸네일 생성, 서버 임시저장, 이중화 인프라.
- 더 무거운 기술보다 이미 고른 단순한 방식을 쓴다: 알림은 30초 폴링(D-72), 메인 피드는 볼 때마다 모아오기(D-73), 배치는 `@Scheduled`(D-12).
- 더 복잡한 방식이 필요해 보이면 plan의 "Complexity Tracking"에 이유를 적고 결정 기록을 남긴다.

## 기술 제약 (요구사항분석서 7장, 모두 확정)

| 화면 | 정적 HTML + JS. 글 상세·블로그 홈·사이트 첫 화면의 og 태그만 서버가 채움 | D-66, D-96, D-100 |

## 개발 흐름 (Spec Kit)

1. `/speckit-specify` — 기능 spec 작성. 요구사항분석서에서 온 기능은 `specs/00N-*/spec.md`에 이미 있다.
2. `/speckit-clarify` — `[NEEDS CLARIFICATION]` 항목을 사람에게 묻고 spec의 Clarifications에 남긴다.
3. `/speckit-plan` — 이 헌법과 맞는지 확인하고 plan, data-model, contracts를 만든다. DB 설계(ERD)는 요구사항이 정리된 뒤에 한다(D-47).
4. `/speckit-tasks` → `/speckit-analyze` → `/speckit-implement`.

## 운영 규칙 (Governance)

- 이 헌법은 다른 개발 관행보다 우선한다. 원칙과 다르게 해야 하면 plan의 Complexity Tracking에 이유를 적고, 사람의 확인을 받아 결정 기록(D-번호)을 남긴다.
- 헌법을 고칠 때는 버전을 올린다: 원칙을 빼거나 뜻을 바꾸면 MAJOR, 원칙·절을 더하면 MINOR, 문구만 다듬으면 PATCH.
- 헌법과 `CLAUDE.md`의 "꼭 지킬 규칙"은 같은 내용을 유지한다. 한쪽을 고치면 다른 쪽도 고친다.
- 요구사항분석서 PDF(2026-10-02)는 원본으로 보관한다. 이후 바뀌는 내용은 `specs/`와 결정 기록에 반영한다 (D-82).
