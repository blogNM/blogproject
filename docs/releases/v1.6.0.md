# Creat_ v1.6.0 업데이트 소식

Creat_가 이제 **서버 두 대**로 돌아가요. 새 버전으로 바꾸는 동안에도 <u>사이트가 끊기지 않는</u> **롤링 무중단 배포**를 실제 사이트에 적용했어요.

> 지금까지는 업데이트할 때마다 10초쯤 사이트가 안 열렸어요. 이제는 <span class="hl-yellow">한 대씩 차례로 바꿔서</span> 그동안 다른 한 대가 손님을 받아요. 글을 쓰고 저장하는 중에도, 구글·네이버·카카오 로그인도 그대로 돼요.

## 업데이트할 때마다 사이트가 잠깐 멈췄어요

**무엇이 불편했나요**

새 버전을 올릴 때마다 옛 서버를 끄고 새 서버를 켜는 사이 **10초쯤 사이트가 열리지 않았어요** (502 에러). 서버가 한 대뿐이라 그 한 대가 멈추면 사이트 전체가 멈췄어요.

**원인**

앱 서버가 한 대뿐이었어요. 끄고 켜는 동안 요청을 대신 받아 줄 서버가 없었어요. 게다가 소셜 로그인은 "로그인하러 갔다 돌아오는" 사이의 확인값을 서버 한 대에 두고 있어서, 서버를 두 대로 늘리면 돌아올 때 다른 서버로 가서 로그인이 실패할 수 있었어요.

**어떻게 고쳤나요**

1. 같은 앱을 **두 대**(8341, 8342) 띄웠어요. 같은 DB·같은 사진 폴더·같은 로그인 열쇠를 써서 어느 쪽이 받아도 결과가 같아요.
2. 학교 정문(Nginx)이 손님을 보내는 **8340번 자리에 우리 안내 데스크(Nginx)** 를 두었어요. 안내 데스크가 두 앱에 번갈아 나눠 주고, 한쪽이 대답이 없으면 다른 쪽으로 다시 보내요.
3. 소셜 로그인 확인값을 **암호화한 쿠키**(브라우저)에 담게 바꿨어요. 어느 앱으로 돌아와도 로그인이 돼요.
4. 새 버전을 올릴 때는 **한 대씩 차례로** 바꿔요. 바꾼 앱이 다시 손님을 받기 시작한 걸 확인한 뒤에 다음 앱을 바꾸고, 새 버전이 안 켜지면 그 자리를 바로 전 버전으로 되돌려요.
5. 앱이 꺼질 때는 **하던 저장을 끝내고** 꺼져요. 이미 앱에 도착한 저장 요청은 다시 보내지 않아서 글이 두 번 올라가지 않아요.

**얼마나 달라졌나요**

> 실제 사이트에 들어오는 요청이 <span class="hl-yellow">두 앱(8341·8342)에 나뉘어</span> 처리돼요. 업데이트 중 멈춤 <u>약 10초 → 0초</u>

![실제 사이트(creat.java21.net)에 10번 요청했을 때 앱 8341·8342가 나눠 받는 모습](/img/releases/v1.6.0/live-split.png)

![한 대를 바꾸는 동안 나머지 한 대가 모두 받는 화면 (모두 200)](/img/releases/v1.6.0/rolling-ok.png)

| | 전 | 후 |
|---|---|---|
| 앱 서버 | 1대 | **2대** |
| 업데이트 중 사이트 | 10초쯤 502 | **끊김 없음** |
| 한 대가 고장 나면 | 사이트 전체가 멈춤 | **다른 한 대가 받음** |
| 소셜 로그인 | 서버 한 대에만 기억 | **어느 서버로 와도 됨** |

## 만들면서 찾은 문제 두 가지

**① 처음에는 한쪽으로만 갔어요**

안내 데스크(Nginx) 직원이 여럿인데 각자 순서를 따로 세서, 매번 첫 번째 서버로만 보냈어요. 직원들이 순서를 함께 세게(`zone`) 고치니 번갈아 나눠졌어요.

![고치기 전: 10번 모두 같은 서버](/img/releases/v1.6.0/lb-before-zone.png)

**② 바꾸는 순서가 너무 빠르면 502가 났어요**

한 대가 켜지자마자 다른 한 대를 껐더니, 안내 데스크가 방금 켜진 서버를 아직 "잠깐 쉬는 중"으로 알고 있어서 **보낼 곳이 없다며 502**를 냈어요. 켜진 뒤 **10초 기다렸다가** 다음 서버를 바꾸게 하니 502가 사라졌어요.

![고치기 전: 기다리지 않고 바꿨을 때 502가 8번](/img/releases/v1.6.0/rolling-502.png)

## 운영 메모

| 항목 | 값 |
|---|---|
| 구조 | 학교 Nginx(443) → `creat-blog-lb`(nginx:alpine, 8340) → `creat-blog-a`(8341, 새벽 작업 담당) · `creat-blog-b`(8342) |
| 학교 Nginx | reload 없이도 되게 8340 자리에 우리 LB를 둠 (D-111). 강사님이 `upstream creat_java21_net {8340, 8341}`을 reload해 주셔서 지금은 학교 Nginx가 8340(LB)과 8341(app-a)로 나눠 보내고, 어느 길이든 동작함 |
| LB 설정 | `zone`, `max_fails=1 fail_timeout=5s`, `proxy_next_upstream error timeout http_502 http_503`(`non_idempotent` 없음), Host·X-Forwarded-* 전달, `X-Upstream` |
| 롤링 | b → 10초 → a, 실패하면 그 자리를 `-prev` 컨테이너로 되돌림. LB 설정이 바뀌면 `nginx -t` 뒤 reload |
| 소셜 로그인 | `CookieOAuth2AuthorizationRequestRepository`(AES-GCM, 3분, `/login/oauth2/code` 경로), 회사 토큰은 저장 안 함 |
| 종료 | graceful shutdown 20초, `docker stop -t 30` |

### 실제 사이트에서 확인한 것 (2026-10-14)

- 배포 [run 40](https://github.com/blogNM/blogproject/actions/runs/38507879485): `lbtest` 정리 → app-b 8342(8초) → `creat-blog-2`를 app-a 8341로(10초) → 8349에서 LB 시험 6/6 200 → 8340 교체 0.6초.
- 맥에서 `curl -D - https://creat.java21.net/` 10번: 앱 8341·8342로 나뉨 (학교 Nginx의 꼬리표 8340이 함께 찍힌 줄은 우리 LB를 거친 요청).
- 구글·네이버·카카오 로그인 모두 정상.
- 로컬에서 같은 구조로 초당 약 75건(글 저장·사진 올리기 포함)을 보내며 롤링: 실패 0건, 중복 저장 0건.

### 확인 방법

```bash
# 내 컴퓨터에서: 두 앱(8341·8342)이 나눠 받는지
for i in $(seq 1 10); do curl -s -o /dev/null -D - https://creat.java21.net/ | grep -i x-upstream; done
# 서버 안에서
for i in $(seq 1 10); do curl -s -o /dev/null -D - http://localhost:8340/ | grep -i x-upstream; done
docker ps --format '{{.Names}}  {{.Status}}'   # creat-blog-lb, creat-blog-a, creat-blog-b
```

### 왜 롤링인가

블루그린·카나리는 배포마다 Nginx가 가리키는 곳이나 비율을 바꾸고 reload해야 하는데, 학교 Nginx reload는 강사님만 할 수 있어요. 롤링은 우리 LB를 8340에 한 번 두면 배포 때 학교 Nginx를 건드리지 않아요.

### 남은 일

- IP별 요청 제한은 앱마다 따로 세서 두 대일 때 최대 2배까지 느슨해짐 (D-83에서 저장 위치 결정).
