# Creat_ v1.4.1 업데이트 소식

새로고침과 검색이 빨라졌어요. 새로고침하면 화면이 **약 6배** 빨리 뜨고, 검색 결과는 **최대 10배** 빨리 와요.

> 고친 것: 새로고침할 때마다 글꼴과 화면 파일 <span class="hl-yellow">약 2MB를 다시 받던 것</span>을 이제는 한 번만 받아요. 검색은 <u>결과는 그대로</u> 두고 찾는 순서만 바꿨어요.

![고치기 전과 후의 속도 비교](/img/releases/v1.4.1/speed-before-after.png)

## 새로고침이 느리고 글자가 깜빡였어요

**무엇이 불편했나요**

어느 화면이든 새로고침하면 1초 넘게 기다려야 했고, 그동안 글자 모양이 한 번 바뀌며 깜빡였어요.

**원인**

보안 설정이 모든 응답에 "저장하지 마세요"라는 표시를 붙이고 있었어요. 그래서 브라우저가 글꼴(2MB)과 화면 파일을 기억하지 못하고 **새로고침할 때마다 처음부터 다시 받았어요**. 글꼴이 늦게 도착하니 글자가 기본 글꼴로 보였다가 바뀌며 깜빡였고요. 화면 파일도 압축하지 않고 보내고 있었어요.

**어떻게 고쳤나요**

- 글꼴·그림처럼 거의 바뀌지 않는 파일은 브라우저가 기억해 두고 다시 받지 않아요.
- 화면 파일은 "바뀐 게 있나요?"만 물어보고, 바뀌지 않았으면 그대로 써요. 업데이트가 있으면 바로 새 파일을 받아요.
- 보내는 내용은 압축해서 보내요.
- 블로그 홈에서 같은 내용을 두 번 받던 것을 한 번으로 줄였어요.

**얼마나 달라졌나요**

| 새로고침 | 고치기 전 | 고친 뒤 | 받는 양 |
|---|---|---|---|
| 메인 | 1,183ms | **206ms** | 2,127KB → 10KB |
| 로그인 | 1,198ms | **119ms** | 2,119KB → 2KB |
| 블로그 홈 | 1,258ms | **212ms** | 2,155KB → 9KB |
| 검색 | 1,156ms | **200ms** | 2,108KB → 6KB |

> <span class="ts-large">새로고침이 약 <span class="hl-yellow">6~10배</span> 빨라졌어요.</span> 글꼴이 처음부터 준비돼 있어 글자도 깜빡이지 않아요.

처음 방문할 때는 글꼴을 한 번 받아야 해서 예전과 비슷해요. 그다음부터 빨라져요.

## 검색 결과가 늦게 나왔어요

**무엇이 불편했나요**

검색어를 넣고 결과가 나올 때까지 잠깐 멈칫했어요. 특히 **태그** 분류를 누르면 더 오래 걸렸어요.

**원인**

검색할 때마다 글·블로그·태그·닉네임 분류의 건수를 함께 세요. 이때 데이터베이스가 공개 블로그가 몇 개인지 잘못 어림잡아, 태그가 달린 글만 보면 될 것을 <u>공개된 글을 모두 하나씩 확인</u>하고 있었어요. 같은 건수를 두 번 세는 곳도 있었어요.

**어떻게 고쳤나요**

- 데이터베이스에 공개 여부·상태가 어떻게 나뉘어 있는지 알려 줘서, 태그에서 바로 그 글들을 찾아가게 했어요.
- 한 번 센 건수는 다시 세지 않아요.
- 검색 결과(어떤 글이 몇 건, 어떤 순서로 나오는지)는 **고치기 전과 똑같아요.**

![검색 결과 화면 (예시 데이터)](/img/releases/v1.4.1/search-results.png)

**얼마나 달라졌나요**

| 검색 (글 3만 개 기준) | 고치기 전 | 고친 뒤 |
|---|---|---|
| '고양이' 태그 | 310ms | **30ms** |
| '서울' 글 (로그인) | 138ms | **43ms** |
| '맛집' 인기순 | 94ms | **34ms** |
| '서울' 글 | 71ms | **32ms** |

> 태그 검색은 <span class="hl-yellow">약 10배</span>, 다른 검색도 2~3배 빨라졌어요.

## 운영 메모

**잰 방법**: 개발 컨테이너에서 `bulk-data.py make`(회원 1,000·블로그 83·글 3만)로 데이터를 넣고, 같은 jar를 고치기 전/후로 띄워 비교. 화면은 Playwright(Chromium, CDP 20Mbps·지연 40ms, 비로그인)로 처음 열기·새로고침을 5~7번씩 재서 가운데 값(load 이벤트 기준). API는 `bulk-data.py bench`(7번, 가운데 값). 운영 서버(creat.java21.net)는 개발 컨테이너 프록시가 막아 직접 재지 못했어요.

| 원인 | 근거 | 고친 곳 |
|---|---|---|
| 정적 파일에 `Cache-Control: no-cache, no-store` (Spring Security 기본 헤더) | `curl -I /vendor/pretendard/PretendardVariable.woff2` → no-store, 새로고침마다 2,057,688B | `StaticCacheConfig`: `/vendor/**` 30일(`STATIC_VENDOR_MAX_AGE`), `/img/**` 7일(`STATIC_IMAGE_MAX_AGE`). 그 밖의 정적 파일 `spring.web.resources.cache.cachecontrol.no-cache=true`(Last-Modified로 304) |
| gzip 꺼짐 | 응답에 Content-Encoding 없음 | `server.compression.enabled=${SERVER_COMPRESSION:true}`, 1KB 이상 html·css·js·json·svg |
| 검색 COUNT가 공개 블로그 글을 모두 훑음 | `EXPLAIN`: `Table scan on b (rows=1 추정)` → `idx_posts_blog_created`로 공개 글 전체, 태그 COUNT 35~60ms·태그 목록 130~250ms | Flyway `V14__search_histograms.sql`: `ANALYZE TABLE blogs UPDATE HISTOGRAM ON visibility, is_hidden, status`, `posts(status)` → `fk_post_tags_tag`에서 출발, 4~7ms |
| 같은 COUNT 두 번 | 고른 분류·블로그 건수를 `PostCards.page`·`blogs()`가 다시 셈 | `PostCards.page(..., long total)`로 분류바 건수를 그대로 씀 |
| 블로그 홈 카테고리 두 번·순서대로 요청 | `/api/blogs/{slug}/categories` 2회, 글 목록이 카테고리 뒤에 시작 | `blog.js`·`post-list.js`가 요청 하나를 같이 쓰고 글 목록과 동시에 받음 |
| js `import` 단계별 대기 | 페이지 js → layout.js → notifications.js 순서로 받음 | 화면 HTML 21개에 `<link rel="modulepreload">` (api.js, layout.js, notifications.js) |

- 검색 결과 동일성: 검색어 11개 × 분류 4 × 정렬 3(2쪽) = 132개 응답을 고치기 전/후 JSON으로 비교해 모두 같음.
- 새로고침 때 API 응답은 그대로 `no-store`. 서버 메모리에 상태를 두지 않음(SCL-01).
- 처음 방문 때 글꼴 2MB는 남음. 글자 범위별 92조각 글꼴도 시험했지만 HTTP/1.1에서 조각 요청이 js·API와 연결을 다퉈 글이 보이는 시점이 0.5→1.0초로 늦어져 넣지 않음.
- 히스토그램은 V14 시점 분포를 저장함. 값 종류가 적은 칸이라 그대로 둬도 되고, 다시 만들려면 같은 `ANALYZE TABLE ... UPDATE HISTOGRAM`을 돌림.

자세한 내용은 [D-109](docs/03-decisions/D-109-속도-캐시-압축.md), [CHANGELOG](CHANGELOG.md)에 있어요.
