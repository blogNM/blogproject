# D-109 화면·검색 속도 (정적 파일 캐시, 압축, 검색 통계)

- 날짜: 2026-10-13
- 관련 요구사항: BRD-08, BRD-09, SCL-01, SEC-12, D-97
- 사용자 요청 (김채림, 2026-10-13): "새로고침 로딩시간이 좀 걸린다 → 거슬림", "서치 하고 나오는 시간이 좀 걸린다"
- 잰 방법: 같은 컴퓨터에서 회원 1,000명·글 3만 개(`bulk-data.py make`)를 넣고, 화면은 Playwright(크롬, 20Mbps·지연 40ms)로 처음 열기·새로고침을 각각 5~7번, API는 `bulk-data.py bench`로 7번씩 재서 가운데 값을 비교했다.
- 찾은 원인:
  1. Spring Security는 Cache-Control을 정하지 않은 응답에 모두 `no-cache, no-store`를 붙인다. 정적 파일도 마찬가지라 **새로고침할 때마다 글꼴(2MB)·js·css·그림을 처음부터 다시 받았다** (화면마다 약 2.1MB). 글꼴이 늦게 와서 새로고침마다 글자 모양이 한 번 바뀌는(깜빡이는) 것도 이 때문이다.
  2. 응답 압축(gzip)이 꺼져 있었다. 화면·js·css·JSON을 그대로 보냈다.
  3. 검색은 분류(글·블로그·태그·닉네임)마다 건수를 센다. MySQL이 공개 여부·상태 칸의 분포를 몰라 "공개 블로그는 1개뿐"이라고 어림잡고, 공개 블로그의 글을 모두 훑은 뒤 글마다 태그를 맞춰 봤다. 그래서 검색어가 무엇이든 태그 건수 세기에 수십 ms, 태그 분류는 300ms 넘게 걸렸다. 고른 분류의 건수와 블로그 건수는 같은 COUNT를 두 번 돌렸다.
  4. 블로그 홈은 카테고리를 두 번 받았고, 글 목록은 카테고리가 온 뒤에야 요청했다.
  5. 화면 js는 `import`를 따라가며 한 단계씩 받았다 (페이지 js → layout.js → notifications.js).
- 선택지:
  1. 파일 이름에 버전(해시)을 붙이고 모든 정적 파일을 오래 캐시한다 — 정적 HTML이라 빌드 도구가 필요하다
  2. 바뀔 일이 거의 없는 글꼴·에디터(`/vendor`)와 그림(`/img`)만 오래 캐시하고, 화면·js·css는 "가지고 있되 쓸 때마다 바뀌었는지 묻기"(`no-cache` + Last-Modified, 안 바뀌었으면 304)로 둔다
- 결정과 이유: 2번. 빌드 도구 없이 바로 효과가 나고, 배포하면 화면·js·css는 바로 새 파일을 받는다.
  - `/vendor/**` 30일(`STATIC_VENDOR_MAX_AGE`), `/img/**` 7일(`STATIC_IMAGE_MAX_AGE`), 나머지 정적 파일 `no-cache` (`StaticCacheConfig`, `spring.web.resources.cache.cachecontrol.no-cache`). 앱이 Cache-Control을 정하면 Spring Security는 덮어쓰지 않는다. API·로그인 응답은 그대로 `no-store`
  - `server.compression` 켬 (`SERVER_COMPRESSION`, 1KB 넘는 html·css·js·json·svg). woff2·사진은 이미 압축돼 있어 뺀다
  - 검색 결과는 그대로 둔다 (같은 검색어·분류·정렬·쪽 132가지 응답이 고치기 전과 똑같음을 확인). Flyway V14로 `blogs(visibility, is_hidden, status)`, `posts(status)`에 히스토그램을 만들어 MySQL이 태그에서 출발하게 한다. 이 칸들은 값 종류가 적고 비율이 거의 바뀌지 않아 한 번 만들어 두면 된다. 분류바 건수를 목록 건수로 그대로 써서 같은 COUNT를 두 번 돌리지 않는다
  - 블로그 홈은 카테고리를 한 번만 받아 메뉴와 글 목록이 함께 쓰고, 글 목록과 카테고리를 동시에 요청한다
  - 화면마다 `<link rel="modulepreload">`로 공통 js(api.js, layout.js, notifications.js)를 페이지 js와 함께 받는다
  - 서버 메모리에 아무것도 두지 않는다 (SCL-01). 캐시는 브라우저, 통계는 MySQL에 있다
- 결과 (새로고침해서 화면이 다 뜰 때까지, 가운데 값): 메인 1,183→206ms, 로그인 1,198→119ms, 블로그 홈 1,258→212ms, 검색 1,156→200ms. 새로고침할 때 받는 양 약 2.1MB → 10KB 이하. 검색 API: 태그 310→30ms, '서울' 71→32ms, 로그인한 회원 '서울' 138→43ms. 자세한 표는 [v1.4.1 노트](../releases/v1.4.1.md)
- 남은 것: 처음 방문할 때는 글꼴 2MB를 한 번 받는다. 글자 범위별로 나눈 글꼴(92조각)도 시험했지만, 조각 요청이 화면 js·API 요청과 연결을 다퉈 글이 보이는 시점이 0.5초 → 1초로 늦어져 넣지 않았다. 비회원이 화면을 열 때 `/api/me`(401) 뒤 로그인 연장 요청이 한 번 더 가는 것(약 1왕복)도 그대로다 (Refresh Token 쿠키는 `/api/auth`에서만 보여 화면이 미리 알 수 없다)
- 이전 내용 → 바꾼 이유: 정적 파일 캐시·압축 설정이 없었음 → 사용자 요청(느림)
