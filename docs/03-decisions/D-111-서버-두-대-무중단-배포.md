# D-111 서버 두 대와 무중단 배포 (우리 Nginx + 롤링)

- 날짜: 2026-10-14
- 관련 요구사항: SCL-01, SCL-03, SEC-04, D-12, D-83(대기), D-103, D-107, D-108
- 계기 (교수 과제, 김채림 요청): 같은 앱을 포트 두 개에 띄우고 Nginx로 요청을 나눈다(이중화). 고르게 나뉘는지 확인하고, 롤링이나 블루-그린으로 무중단 배포를 만든다. 사용자의 최우선 걱정은 "두 대일 때도 소셜 로그인이 되는가"와 "배포 중에도 글을 끊김 없이 저장할 수 있는가".
- 학교 서버 조건 (2026-10-14 확인):
  - 계정에 포트 8340~8349. 앱은 도커(`--network host`)로 돌고 DB는 바깥 MySQL.
  - 학교 공용 Nginx가 https(443)를 풀고 `127.0.0.1:8340`으로 넘긴다. **reload는 강사만 할 수 있다.**
  - 사용자가 `~/nginx/creat.java21.net.conf`를 `upstream {8340, 8341}`로 고쳐 두었지만 reload 전이다. 강사가 언제 reload 할지 모른다.
  - 그때 서버: `creat-blog`(8340, 한 대짜리 deploy.sh가 띄움), 손으로 띄운 `creat-blog-2`(8341), 시험용 `lbtest`(nginx:alpine, 8342).
  - 학교에서 직접 겪은 것: upstream에 `zone`이 없으면 Nginx 일꾼마다 순서를 따로 세어 짧은 연결이 모두 첫 서버로 간다. `max_fails=1 fail_timeout=5s`에서 한 대가 살아나자마자 다른 한 대를 내리면 약 4초 동안 502(no live upstreams)가 난다. 살아난 뒤 10초(fail_timeout보다 길게) 기다리면 없어진다.

## 선택지

1. **학교 Nginx upstream으로 나누기**: 학교 설정에 두 포트를 적고 롤링한다. 설정을 바꿀 때마다 강사에게 reload를 부탁해야 하고, 그 전까지는 8340 한 대만 받는다.
2. **우리 Nginx를 8340에 두기**: 학교 Nginx는 지금처럼 8340만 본다. 8340에 우리 Nginx 컨테이너를 두고 그 뒤에 앱 두 대(8341, 8342)를 둔다. 우리 Nginx는 배포 스크립트가 켜고 검사하고 reload 한다.
3. 블루-그린·카나리: 배포마다 가리키는 곳이나 비중을 바꿔 reload 해야 한다. 1번 위에서는 매번 강사에게 부탁해야 하고, 2번 위에서는 가능하지만 롤링보다 앱이 한 벌 더 필요하다(포트·메모리).

## 결정과 이유

**2번 + 롤링.** 학교 Nginx reload는 강사만 할 수 있어 우리가 기댈 수 없다. 2번은 학교 쪽이 이미 하고 있는 일(8340으로 넘기기)만 필요하므로 강사 reload 없이 오늘 바로 쓸 수 있다. 사용자가 고쳐 둔 학교 설정(`upstream {8340, 8341}`)이 나중에 reload 되어도 그대로 동작한다(8341은 같은 앱 app-a). `deploy.sh`는 학교 설정 파일을 지금처럼 **없을 때만 만들고, 있으면 건드리지 않는다.**

```
학교 Nginx(443) → 8340 우리 Nginx creat-blog-lb (nginx:alpine) ─┬→ 8341 creat-blog-a (app-a, 새벽 정리 작업)
                                                                 └→ 8342 creat-blog-b (app-b)
```

### 우리 Nginx (`deploy.sh`가 `~/creat-blog/lb/default.conf`에 만들고 읽기 전용으로 붙임)

- `upstream creat_blog { zone creat_blog 64k; server 127.0.0.1:8341 max_fails=1 fail_timeout=5s; server 127.0.0.1:8342 ...; }`. `zone`은 위 학교 실험 결과.
- `proxy_next_upstream error timeout http_502 http_503; proxy_next_upstream_tries 2; proxy_connect_timeout 2s;` 읽기 60초, 보내기 60초.
- **`non_idempotent`는 넣지 않는다.** 이미 앱에 보낸 POST(글 저장 등)는 다른 앱에 다시 보내지 않아 두 번 저장되지 않는다. 내려가는 앱은 graceful shutdown으로 듣기 소켓부터 닫으므로 새 연결은 거절되고(아직 안 보낸 요청), 그런 POST는 다른 앱으로 넘어간다.
- upstream `keepalive`는 넣지 않는다(요청마다 새 연결). 쥐고 있던 연결로 보낸 POST가 앱이 꺼지는 순간 실패하는 일을 막는다.
- 원래 Host·scheme·손님 IP를 넘긴다: `Host $host`, `X-Forwarded-For $proxy_add_x_forwarded_for`. `X-Forwarded-Proto`와 `X-Real-IP`는 `map`으로 이 서버 안(127.0.0.1, ::1)에서 온 값만 그대로 넘기고, 아니면 우리 Nginx가 본 `$scheme`·`$remote_addr`를 쓴다.
- `client_max_body_size 20m`(사진 한 번에 10MB보다 큼), `proxy_buffer_size 16k`(로그인 쿠키·보안 헤더가 많은 응답), `add_header X-Upstream $upstream_addr always`, `server_tokens off`.
- 설정은 폴더째 붙인다(파일 하나만 붙이면 바꾼 파일이 컨테이너에 안 보인다). 바뀌면 `docker exec creat-blog-lb nginx -t` 통과 뒤 `nginx -s reload`, 통과 못 하면 전 설정으로 돌린다.

### 앱이 프록시 두 번을 거쳐도 맞게 보는지

- `server.forward-headers-strategy=native`(학교 도메인이 있으면 deploy.sh가 넣음): 톰캣 RemoteIpValve가 `X-Forwarded-For`를 오른쪽부터 읽으며 서버 안 주소(127.0.0.1 등)를 건너뛴다. `손님IP, 127.0.0.1`에서 손님 IP를 고르므로 IP별 요청 제한·로그는 그대로 맞다.
- `X-Forwarded-Proto: https`를 받으면 요청이 https·443으로 보인다. 소셜 로그인 `redirect-uri`는 `{baseUrl}/login/oauth2/code/{registrationId}`라 `https://creat.java21.net/login/oauth2/code/{google|naver|kakao}`가 된다(개발 컨테이너에서 학교 Nginx 역할 → 우리 Nginx → 앱으로 확인).
- `og` 태그·메일 링크는 원래 `APP_BASE_URL`을 쓰므로 영향 없음.

### 앱 두 대

| 컨테이너 | 이름(`INSTANCE_ID`) | 포트 | 새벽 정리 작업 |
|---|---|---|---|
| `creat-blog-a` | app-a | `APP_PORT_A` (기본 APP_PORT+1 = 8341) | 돈다 (`APP_JOBS_ENABLED=true`) |
| `creat-blog-b` | app-b | `APP_PORT_B` (기본 APP_PORT+2 = 8342) | 안 돈다 |

- 같은 이미지, 같은 `secrets.env`·`runtime.env`, 같은 사진 폴더. 서버 안(`SERVER_ADDRESS=127.0.0.1`)에서만 받는다.
- `GET /api/health`: 로그인 없이 `{"status":"UP","instance":"app-a"}`. DB에 `SELECT 1`만 묻고 안 되면 503. 모든 응답에 `X-Instance` 헤더.
- 새벽 4시 정리 작업 네 개는 app-a에서만 등록한다(`app.jobs.enabled`). ShedLock(SCL-03)은 그대로 두어 설정을 잘못 넣어도 한 번만 돈다.
- `server.shutdown=graceful`, `SHUTDOWN_TIMEOUT=20s`, `docker stop -t 30`(20초보다 길게). 처리 중인 글 저장·사진 올리기를 마치고 내려간다. 우리 Nginx가 요청 본문을 다 받은 뒤 앱에 넘기므로(요청 버퍼링) 느린 업로드도 앱에서는 짧다.

### `deploy.sh` 순서

**보통 배포**: b를 새 이미지로 바꾸고 `/api/health` 200을 기다린 뒤 `SETTLE_SECONDS`(10초, `fail_timeout` 5초보다 길게) 기다리고 a를 바꾼다. 바꿀 자리의 지금 컨테이너는 지우지 않고 `<이름>-prev`로 멈춰 두었다가, 새 것이 안 뜨면 그대로 다시 켠다(같은 이미지·같은 설정). 뜨다가 죽어 도커가 다시 켜면 바로 실패로 본다. a에서 실패하면 b도 전 컨테이너로 돌린다. `latest` 태그는 돌고 있는 이미지로 돌려 둔다. 우리 Nginx는 켜 둔 채, 설정이 바뀌었을 때만 검사 뒤 reload 한다.

- 같은 스크립트를 몇 번 돌려도 되고, 예전·새 컨테이너가 섞여 있어도 정리한다: 끊긴 배포가 남긴 `-prev`는 처음에 되돌리고, 응답하지 않는 자리를 먼저 바꾸며, 멈춘 우리 Nginx는 포트가 비어 있으면 먼저 켠다.
- `flock`으로 배포 두 개가 겹치지 않게 한다.

**처음 한 번 (한 대 → 새 구조)**:

1. `lbtest`를 지운다.
2. app-b를 8342에 새 이미지로 띄우고 준비를 기다린다.
3. `creat-blog-2`(8341)를 멈추고(지우지 않음) app-a를 띄워 준비를 기다린다. 안 되면 `creat-blog-2`를 다시 켠다.
4. 빈 포트 `LB_CHECK_PORT`(8349)에 같은 설정의 시험 Nginx를 띄워 6번 물어 모두 200이고 8341·8342 둘 다 받는지 본 뒤 지운다.
5. `SWAP_SETTLE_SECONDS`(12초, 학교 Nginx 기본 `fail_timeout` 10초보다 길게) 기다린다. 우리 Nginx 컨테이너를 미리 만들어 두고, `creat-blog`(8340)의 재시작 정책을 끈 뒤 종료 신호를 보내 8340이 비자마자 우리 Nginx를 켠다.
6. 8340으로 `/api/health` 200이면 `creat-blog`, `creat-blog-2`를 지운다. 우리 Nginx가 안 뜨면 지우고 `creat-blog`를 다시 켠다(그 컨테이너가 없으면 새 이미지 앱을 8340에 띄운다).

- 1~4에서 실패하면 8340은 손대지 않는다. 앞의 단계가 하나라도 실패하면 `creat-blog`가 계속 8340에서 받는다.
- Flyway 마이그레이션은 처음 뜨는 새 앱 한 대가 돌린다. 마이그레이션은 이전 버전(아직 남은 한 대)과도 맞아야 한다(컬럼 추가는 바로, 지우기·이름 바꾸기는 다음 릴리스에서).
- 받는 값: `APP_PORT`(우리 Nginx, 기본 8340), `APP_PORT_A`·`APP_PORT_B`(기본 +1·+2), `LB_CHECK_PORT`(+9), `SETTLE_SECONDS`, `SWAP_SETTLE_SECONDS`, `FAIL_TIMEOUT`, `SHUTDOWN_SECONDS`, `STOP_TIMEOUT`, `LB_IMAGE`(nginx:alpine). `reset_db`와 다른 시크릿은 그대로.

## 확인한 결과 (2026-10-14, 개발 컨테이너)

학교 서버 모양을 그대로 만들었다: HEAD(main) 이미지로 예전 `deploy.sh`가 띄운 `creat-blog`(8340), 손으로 띄운 `creat-blog-2`(8341), `lbtest`(8342), https를 풀고 8340(또는 8340·8341)으로 넘기는 학교 Nginx 역할(nginx 1.24, 일꾼 4개), MySQL 8.0, 테스트 데이터. 부하는 학교 Nginx로 초당 약 75번: GET 4명(`/`, `/api/notices`, `/api/blogs`, `/api/feed`, `/blog/foodie-seoul`), 로그인한 회원 2명의 글 저장(POST), 1명의 사진 올리기(POST). 실패 = GET 200, POST 200이 아닌 응답이나 연결 오류.

- 그 뒤 기다림을 줄였다: 우리 Nginx 컨테이너가 꺼지면 바로 실패로 본다. 옛 앱이 다시 뜨는 시간(약 15초)은 남는다. 같은 이미지·설정을 4단계에서 미리 시험하므로 일어나기 어렵다.
- 섞인 상태(위 실패 뒤: 8340 옛 `creat-blog`, 새 a·b, 우리 Nginx 없음)에서 다시 돌리면 우리 Nginx로 옮겨졌다(0.24초 끊김). 우리 Nginx를 멈춰 두거나 `creat-blog-a-prev`만 남긴 상태에서도 정리되었다.
- 나누기: 보통 배포 중 app-a 2,237 · app-b 2,196.
- 실패한 POST 502 (처음 옮길 때 3건)는 DB에 생기지 않았다. 다시 보내지 않으므로 중복도 없다.
- 소셜 로그인: 학교 Nginx를 거친 `redirect_uri`가 세 회사 모두 `https://creat.java21.net/login/oauth2/code/...`. 한 앱(8341·8342)에서 받은 `OAUTH2_REQUEST` 쿠키와 state로 **세 번째 앱**(같은 비밀 키, 8343)의 `/login/oauth2/code/kakao`·`naver`를 부르면 state 검사를 통과해 회사 토큰 주소까지 갔다(가짜 키라 `invalid_token_response`로 끝). 쿠키 없이 부르면 그 전에 실패한다. 실제 회사 로그인 끝까지는 서버에 올린 뒤 확인해야 한다.
- `docker stop`하면 앱 로그에 `Commencing graceful shutdown` → `Graceful shutdown complete`.

## 이전 내용 → 바꾼 이유

서버 한 대, 배포 때 컨테이너를 내렸다 올려 약 15초 접속이 끊김, 소셜 로그인 요청 값은 세션. 이 결정의 초안은 학교 Nginx upstream(8340·8341)에 기대는 롤링이었다 → 학교 Nginx reload는 강사만 할 수 있어 8340에 우리 Nginx를 두는 구조로 바꿈. 교수 과제(이중화·무중단 배포)와 SCL-01(서버 메모리에 상태를 두지 않음)
