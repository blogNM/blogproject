# D-127 보안 보강 (속도·기능은 그대로)

- 날짜: 2026-10-16
- 관련 요구사항: SEC-03, SEC-08, SEC-12, USR-05, USR-07, D-80, D-92
- 사용자 요청 (김채림, 2026-10-16): "보안을 좀 더 강화해줘. 속도가 느려지지 않고 기능에 문제가 되지 않는 선에서 보안 강화가 가능할까?"
- 점검 결과: JWT·HttpOnly 쿠키, CSRF, bcrypt, 로그인 잠금·사람 확인, 본문 jsoup 거르기, 사진 형식 검사, 링크 미리보기 SSRF 막기는 이미 갖춰져 있었다. 그 사이에 남은 틈 여섯 가지를 막는다
- 결정
  1. **로그인 뒤 돌아갈 주소(`login.html?next=`)**: 글자로 `/`·`//`만 보던 검사를 실제로 풀어 본 주소의 출처(origin) 비교로 바꾼다. 브라우저는 주소 속 탭·줄바꿈을 지워 `/%09/evil.com`이 `//evil.com`(다른 사이트)이 되기 때문이다
  2. **지금 비밀번호 확인 횟수**: 비밀번호 변경·탈퇴(회원)와 관리자 비밀번호 변경에서 지금 비밀번호를 맞혀 보는 일을 회원·관리자마다 1시간에 10번까지 받는다(`RATE_PASSWORD_CHECK_PER_HOUR`). 로그인 쿠키를 빼앗겨도 비밀번호를 알아내 계정을 가로채거나 탈퇴시키지 못한다
  3. **관리자 로그인 응답 시간**: 없는 아이디에도 같은 bcrypt 비교를 한다. 회원 로그인은 이미 그렇게 하고 있었다. 응답 시간 차이로 관리자 아이디가 있는지 알아내지 못한다
  4. **사진 올리기 횟수**: 회원마다 1분에 30장까지(`RATE_UPLOAD_PER_MINUTE`). 글 하나에 10장이라 평소 쓰기에는 걸리지 않고, 쉬지 않고 올려 서버 디스크를 채우는 것만 막는다
  5. **보안 헤더 두 개 추가**: `Permissions-Policy`로 쓰지 않는 브라우저 기능(카메라·마이크·위치·결제 등)을 끄고, `Cross-Origin-Opener-Policy: same-origin`으로 다른 사이트가 연 창에서 우리 화면을 조작하지 못하게 한다. 소셜 로그인은 팝업이 아니라 같은 창 이동이라 영향이 없다
  6. **링크 미리보기 내부망 막기**: IPv6 안에 IPv4를 담는 NAT64(`64:ff9b::/96`)·6to4(`2002::/16`) 주소도 안에 든 IPv4로 다시 판단해 내부망이면 거절한다
- 속도: 모두 메모리 카운터 한 번, 헤더 몇 줄, 이미 하던 주소 검사에 비교 몇 번을 더한 것이라 DB 조회나 바깥 요청이 늘지 않는다. 관리자 로그인의 bcrypt 비교는 없는 아이디일 때만 늘고, 있는 아이디와 같은 시간이 걸린다
- 고르지 않은 것
  - Refresh Token을 쓸 때마다 바꾸기(rotation): 탭 여러 개가 동시에 갱신하면 서로 로그아웃시키는 일이 생겨 "기능에 문제 없이"를 지키기 어렵다
  - 링크 미리보기에서 DNS를 한 번만 풀어 그 IP로 접속하기(DNS rebinding 막기): Java HttpClient가 접속 IP를 따로 정할 수 없어 HTTPS 인증서 확인을 바꿔야 한다. 저장할 때 한 번 받는 기능이고 응답 크기·시간 제한이 있어 이번에는 두었다
  - `Cross-Origin-Resource-Policy`: 다른 사이트(카카오톡·SNS 미리보기 등)가 우리 사진을 보여 주지 못할 수 있다
  - 요청 제한 카운터를 서버 두 대가 함께 쓰기: D-83(공용 저장소) 결정을 기다린다. 지금은 서버마다 따로 세어 실제 한도는 최대 두 배다
