# DB 구조 바꾸기 규칙 (Flyway, D-132)

배포는 앱 두 대를 한 대씩 바꾼다(D-111). 새 앱(b)이 뜨면서 Flyway가 DB 구조를 바꾸는 동안, **옛 앱(a)은 아직 옛 코드로 손님을 받는다.** 그래서 한 번의 배포에서 바꾸는 DB 구조는 옛 코드도 그대로 돌아가는 모양이어야 한다.

## 한 번에 해도 되는 것

| 바꾸는 일 | 이유 |
|---|---|
| 새 표 만들기 | 옛 코드는 그 표를 모른다 |
| 새 칸 추가 (`NULL` 허용이거나 `DEFAULT` 있음) | 옛 코드의 `INSERT`가 그 칸을 빼도 들어간다 |
| 색인 추가 | 읽는 결과는 같다. 큰 표면 배포가 길어질 수 있으니 행 수를 먼저 본다 |
| `CHECK` 허용 값 늘리기 | 옛 코드가 쓰는 값은 그대로 들어간다 |
| 칸 길이 늘리기 (`VARCHAR(100)` → `200`) | 옛 값이 모두 들어간다 |

## 두 번에 나눠야 하는 것 ("늘리고 → 나중에 줄이기")

| 하고 싶은 일 | 1번째 배포 | 2번째 배포 (1번째가 두 대 모두 올라간 뒤) |
|---|---|---|
| 칸 이름 바꾸기 | 새 칸 추가 + 옛 칸 값 복사, 코드는 두 칸 모두 쓰고 새 칸을 읽음 | 옛 칸 지우기 |
| 칸 지우기 | 코드에서 그 칸 쓰기를 모두 뺌 (칸은 둠) | 칸 지우기 |
| 표 지우기 | 코드에서 그 표 쓰기를 모두 뺌 | 표 지우기 |
| `NOT NULL` 칸 추가 (기본값 없음) | `NULL` 허용으로 추가, 코드는 늘 값을 넣음, 빈 행 채우기 | `NOT NULL`로 바꾸기 |
| `CHECK` 허용 값 줄이기, 칸 길이 줄이기 | 코드가 그 값을 더 쓰지 않게 하고 남은 행을 고침 | 제약 바꾸기 |

1번째 배포 뒤 바로 2번째를 합치지 말고, 두 대가 모두 새 코드인지(`서버 상태 확인` 워크플로의 컨테이너 이미지) 본 다음 올린다.

## 그 밖에

- 파일 이름은 `V{다음 번호}__{영어_설명}.sql`. 한 번 main에 들어간 파일은 고치지 않는다(Flyway 체크섬이 달라져 앱이 뜨지 않음). 고칠 것은 새 번호로 만든다
- 마이그레이션은 배포 전 DB 백업(`before-deploy-*`, D-128) 뒤에 돈다. 잘못되면 [백업-복구.md](백업-복구.md)로 되돌린다
- 바꾼 표는 `docs/04-design/schema.sql`과 `ERD.md`에도 함께 적는다
- 테스트는 빈 DB에서 처음부터 모든 마이그레이션을 돌리므로, 학교 서버처럼 MySQL 8.0에서도 되는 문법만 쓴다
