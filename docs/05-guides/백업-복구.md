# 백업과 되돌리기 (D-129)

## 어디에 백업이 있나

| 언제 | 무엇 | 어디에 | 얼마나 |
|---|---|---|---|
| 매일 새벽 5:10 (한국 시간) | DB | Actions 보관함 `db-날짜-시각` + 서버 `~/creat-blog/backups/daily-*.sql.gz` | Actions 14일(`BACKUP_RETENTION_DAYS`), 서버 최근 14개(`BACKUP_KEEP_DAILY`) |
| 일요일 새벽 5:10, 손으로 돌릴 때 | 올린 사진(`data/uploads`) | Actions 보관함 `uploads-날짜-시각` | 14일 |
| 배포할 때마다 | DB | 서버 `~/creat-blog/backups/before-deploy-*.sql.gz` | 최근 14개(`BACKUP_KEEP`) |
| `reset_db=reset`으로 지우기 전 | DB | 서버 `~/creat-blog/backups/before-reset-*.sql.gz` | 위와 같이 셈 |

Actions 보관함은 서버 밖(깃허브)에 있어서 서버 디스크가 망가져도 남습니다. 워크플로는 `.github/workflows/backup.yml`, 서버에서 도는 스크립트는 `app/deploy/backup.sh`입니다.

## 지금 바로 백업하기

GitHub 저장소 → Actions → **매일 백업** → Run workflow. "올린 사진도 함께 가져오기"를 켜면 사진도 받습니다. 큰 변경 전에 한 번 돌려 두면 좋습니다.

## 백업 받기

1. Actions → **매일 백업** → 원하는 날짜의 실행 → 맨 아래 Artifacts에서 `db-…`(또는 `uploads-…`)를 누르면 zip으로 받아집니다.
2. zip을 풀면 `db.sql.gz`(사진은 `uploads.tar.gz`)가 나옵니다.
3. `BACKUP_PASSWORD` 시크릿을 넣어 두었다면 파일 끝이 `.gpg`입니다. 먼저 풉니다.

```bash
gpg --decrypt db.sql.gz.gpg > db.sql.gz   # 비밀번호를 물어봄
```

## DB 되돌리기

되돌리면 지금 DB 내용은 백업 시점으로 바뀝니다. 되돌리기 전에 지금 상태도 한 번 백업해 두세요(위 "지금 바로 백업하기").

서버에 SSH로 들어가서:

```bash
# 받은 파일을 서버에 올렸다면 그 경로, 서버에 있는 것을 쓰면 ~/creat-blog/backups/daily-….sql.gz
F=~/creat-blog/backups/daily-20261118-051000.sql.gz
gzip -dc "$F" | docker run --rm -i --network host -e MYSQL_PWD='DB비밀번호' mysql:8.0 \
  mysql -h DB주소 -P DB포트 -u DB아이디 --protocol=TCP DB이름
```

덤프에는 표마다 `DROP TABLE IF EXISTS`가 들어 있어서 같은 이름의 표를 백업 내용으로 바꿉니다. 백업 뒤에 새로 생긴 표(새 마이그레이션)가 있으면 그 표는 남으므로, 그럴 때는 그 버전 이전 앱으로 배포하거나 배포 워크플로의 `reset_db`로 비운 뒤 넣습니다.

## 사진 되돌리기

```bash
cd ~/creat-blog/data
tar -xzf ~/uploads.tar.gz        # uploads/ 폴더로 풀림. 같은 이름 파일은 덮어씀 (파일 이름이 UUID라 겹치지 않음)
```

## 살펴볼 것

- 백업이 실패하면 깃허브가 실패 메일을 보냅니다. Actions 탭에서 빨간 ✕가 있는지 가끔 확인합니다.
- 깃허브 무료 계정의 Actions 저장 용량(비공개 저장소, 약 500MB)을 넘으면 올리기가 실패합니다. 사진이 많아지면 `BACKUP_RETENTION_DAYS`를 줄이거나 다른 보관처를 정합니다.
- 서버에 남는 백업은 같은 디스크에 있으므로 디스크 고장에는 소용없습니다. 빠르게 되돌리는 용도입니다.
