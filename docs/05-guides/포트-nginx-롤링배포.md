# 포트 · Nginx · 롤링 무중단 배포 쉽게 정리

오늘 서버에서 직접 해 본 것(포트 두 개 → Nginx로 분산 → 한 대 꺼도 버티기 → 롤링 배포)을 처음부터 순서대로 정리했어요.

---

## 1. 포트는 뭔가요

> **IP 주소(도메인)는 건물 주소, 포트는 그 건물의 호수**예요.

- 서버 컴퓨터 한 대(건물) 안에 프로그램이 여러 개 돌아요. 각 프로그램은 **자기 호수(포트 번호)** 에서 손님을 기다려요.
- 요청을 보낼 때는 "건물 주소 + 호수"를 같이 적어야 해요. 예: `localhost:8340` = "이 건물 8340호".
- 한 호수에는 프로그램 하나만 들어갈 수 있어요. 그래서 같은 앱을 두 개 띄우려면 **호수를 다르게** 줘야 해요.

우리 서버에서 쓰는 호수:

| 포트 | 누가 쓰나 | 하는 일 |
|---|---|---|
| **443** | 학교 Nginx | 바깥(인터넷)에서 들어오는 https 손님을 받는 정문 |
| **8340** | `creat-blog` (app1) | 블로그 앱 1번 |
| **8341** | `creat-blog-2` (app2) | 블로그 앱 2번 (같은 프로그램, 같은 DB) |
| **8342** | `lbtest` (테스트용 Nginx) | 강사님 없이 분산을 시험해 본 임시 정문 |

- `docker ps`에 포트가 안 보였던 이유: 컨테이너를 `--network host`로 띄워서 컨테이너가 **서버의 호수를 그대로** 써요. 따로 연결(포트 매핑)할 필요가 없어서 표시가 비어 있어요.
- 서버 안에서 `curl https://creat.java21.net`이 `000`이 나온 건, 그 서버에서 자기 도메인으로 바깥을 돌아 들어오는 길이 막혀 있어서예요. 서버 안에서는 `localhost:포트`로 확인하면 돼요.

---

## 2. Nginx는 뭔가요

> **Nginx는 건물 1층의 안내 데스크(카운터)** 예요. 손님은 안내 데스크만 보고, 뒤에서 몇 호가 일하는지 몰라요.

Nginx가 하는 일:
1. **정문 지키기**: 443(https)으로 들어온 손님을 받아요. 자물쇠(SSL 인증서)도 여기서 풀어요. 그래서 앱은 https를 몰라도 돼요.
2. **안쪽으로 넘기기 (리버스 프록시)**: 받은 요청을 뒤의 앱(8340, 8341)에 넘기고, 앱의 대답을 손님에게 돌려줘요.
3. **나눠 주기 (로드 밸런싱)**: 앱이 여러 개면 돌아가며 나눠 줘요.
4. **장애 피하기**: 한 앱이 대답을 안 하면 다른 앱으로 다시 넘겨요.

### 요청 하나가 지나가는 길

```
브라우저 ──https──▶ creat.java21.net:443 (Nginx 안내 데스크)
                         │  upstream creat_java21_net 에서 차례 고르기
                         ├──▶ 127.0.0.1:8340 (app1) ─┐
                         └──▶ 127.0.0.1:8341 (app2) ─┤── 같은 MySQL DB, 같은 사진 폴더
                                                     │
브라우저 ◀──── 응답 + "X-Upstream: 127.0.0.1:834x" ◀──┘
```

### 우리가 넣은 설정 한 줄씩

```nginx
upstream creat_java21_net {          # "앱 묶음"에 이름 붙이기
    zone creat_java21_net 64k;       # 직원들이 순서를 같이 적는 공용 메모장
    server 127.0.0.1:8340 max_fails=1 fail_timeout=5s;
    server 127.0.0.1:8341 max_fails=1 fail_timeout=5s;
}
...
location / {
    proxy_pass http://creat_java21_net;                   # 요청을 묶음으로 넘김
    proxy_next_upstream error timeout http_502 http_503;  # 실패하면 다른 앱으로 다시
    proxy_connect_timeout 2s;                             # 2초 안에 안 받으면 실패로 봄
    add_header X-Upstream $upstream_addr always;          # 누가 받았는지 응답에 적기
}
```

| 설정 | 쉬운 말 |
|---|---|
| `upstream` | "이 요청은 이 앱들 중 하나에게"라는 명단 |
| `server ...:8340` | 명단에 있는 앱 하나 |
| `max_fails=1 fail_timeout=5s` | 한 번 실패하면 **5초 동안 그 앱은 건너뜀**. 5초 뒤 한 번 슬쩍 다시 보내 봄 |
| `proxy_next_upstream` | 실패한 요청을 **다른 앱에게 다시 보내서** 손님은 실패를 모르게 함 |
| `zone` | Nginx 직원(worker) 여럿이 순서를 함께 셈. 없으면 직원마다 따로 세서 한쪽(8340)에만 몰림 |
| `X-Upstream` | 확인용 꼬리표. `8341, 8340`처럼 두 개면 "8341 실패 → 8340이 대신 받음" |

> 오늘 처음에 8340만 10번 나왔던 건 `zone`이 없어서였어요. 넣고 나니 번갈아 나왔어요.

## 3. 이중화 (한 대 꺼져도 버티기)

- 앱이 한 대면 그 한 대가 죽을 때 사이트도 같이 죽어요.
- 두 대를 같은 DB, 같은 사진 폴더, 같은 비밀 키(`secrets.env`의 JWT 키)로 띄우면 **어느 쪽이 받아도 결과가 같아요.** 그래서 한쪽이 꺼져도 다른 쪽이 다 받아요.
- 오늘 `docker stop creat-blog-2` 해 보니 전부 `200`에 `8340`만 나왔죠. 이게 이중화예요.

**두 대가 똑같이 동작하려면 지켜야 할 것**
- 로그인 정보는 쿠키(JWT)에 들고 다녀서 어느 앱이 받아도 알아봐요.
- 서버 메모리에 따로 기억해 두는 값이 없어야 해요 (프로젝트 규칙 SCL-01).
- 소셜 로그인 중간값(state 등)은 서버 세션 대신 잠긴(암호화한) 쿠키에 담아요. 그래서 로그인 버튼을 누른 앱과 구글·네이버·카카오에서 돌아온 요청을 받은 앱이 달라도 로그인돼요 (7장, D-111).

## 4. 무중단 배포는 왜 필요한가요

**지금까지의 배포 (앱 한 대)**

```
옛 앱 끄기 ──▶ (10초쯤 아무도 없음 = 502 에러) ──▶ 새 앱 켜기
```

배포할 때마다 그 몇 초 동안 사이트가 안 열려요. **무중단 배포**는 이 빈 시간을 없애는 방법이에요. 앱이 두 대 이상 있어야 가능해요.

## 5. 롤링 배포는 어떻게 동작하나요

> **한 대씩 차례로 바꾸기.** 바꾸는 동안 나머지 한 대가 손님을 다 받아요.

| 단계 | 8340 (app1) | 8341 (app2) | 손님이 받는 응답 |
|---|---|---|---|
| ① 평상시 | 켜짐 (옛 버전) | 켜짐 (옛 버전) | 200 · 번갈아 |
| ② app2 교체 | **혼자 다 받음** | 재시작 중 | 200 · 8340만 |
| ③ 확인 + 10초 대기 | 받는 중 | 켜짐 (새 버전) | 200 · 다시 번갈아 |
| ④ app1 교체 | 재시작 중 | **혼자 다 받음** | 200 · 8341만 |
| ⑤ 완료 | 켜짐 (새 버전) | 켜짐 (새 버전) | 200 · 번갈아 |

오늘 쓴 명령:

```bash
docker restart -t 30 creat-blog-2                                              # ② app2 교체
until curl -fs -o /dev/null http://localhost:8341/; do sleep 2; done; sleep 10 # ③ 켜졌나 확인 + 10초
docker restart -t 30 creat-blog                                                # ④ app1 교체
until curl -fs -o /dev/null http://localhost:8340/; do sleep 2; done           # ⑤ 켜졌나 확인
```

### 왜 ③에서 10초를 기다리나요 (오늘 직접 겪은 것)

- **첫 번째 시도 (대기 없음)**: `502 Bad Gateway`가 8줄 나왔어요.
  - ②에서 app2가 꺼져 있을 때 Nginx가 보낸 요청이 실패했어요. 그래서 Nginx 메모에 "8341은 5초 쉬기"가 적혔어요.
  - app2가 다 켜지자마자 app1을 껐는데, Nginx는 **아직 8341을 쉬는 중으로 보고 있었어요.**
  - 두 대 다 못 쓴다고 판단해서 502를 냈어요 (`X-Upstream: app` = 보낼 곳 없음).
- **두 번째 시도 (10초 대기)**: 5초 표시가 풀리고 8341이 다시 손님을 받는 걸 확인한 다음에 app1을 꺼서, **처음부터 끝까지 모두 200**이었어요.

> 핵심: "새 앱이 켜졌다"로는 부족하고, **"안내 데스크(Nginx)가 새 앱에게 다시 보내기 시작했다"** 까지 확인한 다음에 다른 한 대를 꺼야 해요.

## 6. 롤링 · 블루그린 · 카나리 비교

| 방식 | 하는 방법 | 우리 환경에서 |
|---|---|---|
| **롤링** ✅ | 같은 자리의 앱을 한 대씩 새 버전으로 바꿈 | Nginx 설정을 **한 번만** 해 두면 끝. 배포할 때마다 강사님께 부탁할 필요 없음 |
| 블루그린 | 새 버전 묶음(그린)을 다른 포트에 통째로 띄운 뒤 Nginx가 가리키는 곳을 블루에서 그린으로 바꿈 | 배포할 때마다 Nginx 설정 변경과 reload가 필요해서 매번 강사님께 부탁해야 함 |
| 카나리 | 새 버전에 일부(예: 10%)만 보내 보고 괜찮으면 늘림 | 비율을 바꿀 때마다 Nginx 설정 변경이 필요해서 매번 부탁해야 함 |

- 롤링의 단점: 바꾸는 잠깐 동안 옛 버전과 새 버전이 **같이** 돌아요. 그래서 DB 구조를 크게 바꾸는 배포는 옛 버전도 견딜 수 있게 나눠서 해야 해요.
- 블루그린의 장점: 문제가 생기면 Nginx를 다시 블루로 돌리기만 하면 돼서 되돌리기가 가장 빨라요.

## 7. 이제는 자동이에요: 우리 Nginx(8340) + 앱 두 대(8341, 8342)

학교 Nginx를 다시 읽게(reload) 하는 건 **강사님만** 할 수 있어요. 그래서 학교 Nginx는 지금처럼 **8340 하나만** 보게 두고, 8340 자리에 **우리 Nginx**를 세웠어요. 우리 Nginx는 우리 컨테이너라 배포 스크립트가 마음대로 켜고 다시 읽힐 수 있어요 (D-111).

```
브라우저 ──https──▶ 학교 Nginx (443, 강사님 관리)
                         │  지금처럼 127.0.0.1:8340 으로만 넘김 (reload 필요 없음)
                         ▼
                    우리 Nginx  creat-blog-lb  (8340, nginx:alpine)
                         │  upstream creat_blog: 번갈아 + 실패하면 다른 쪽으로
                         ├──▶ creat-blog-a  (8341, app-a) ─┐
                         └──▶ creat-blog-b  (8342, app-b) ─┴── 같은 이미지·같은 DB·같은 사진 폴더·같은 secrets.env
```

| 포트 | 컨테이너 | 하는 일 |
|---|---|---|
| **8340** | `creat-blog-lb` | 우리 안내 데스크. 학교 Nginx가 보내는 곳 |
| **8341** | `creat-blog-a` (app-a) | 블로그 앱. 새벽 4시 정리 작업도 이쪽에서만 돌아요 (`APP_JOBS_ENABLED=true`) |
| **8342** | `creat-blog-b` (app-b) | 블로그 앱. 정리 작업은 꺼 둠 |
| 8349 | (잠깐) `creat-blog-lb-check` | 처음 한 번, 우리 Nginx를 미리 시험해 보는 빈 호수 |

- 앱 두 대는 서버 안(`127.0.0.1`)에서만 받아요. 밖에서는 우리 Nginx를 거쳐야 해요.
- 응답 꼬리표: `X-Upstream: 127.0.0.1:8341`(우리 Nginx가 붙임), `X-Instance: app-a`(앱이 붙임). 개발자 도구나 `curl -I`로 누가 받았는지 바로 봐요.
- 준비됐는지는 `GET /api/health`로 물어봐요. DB까지 되면 `{"status":"UP","instance":"app-a"}`와 200, DB가 안 되면 503이에요.
- 학교 Nginx 설정 파일(`~/nginx/creat.java21.net.conf`)은 **건드리지 않아요.** 손으로 고쳐 둔 `upstream {8340, 8341}`을 강사님이 언젠가 reload 해도 괜찮아요. 그때는 학교 Nginx가 8340(우리 Nginx)과 8341(app-a)에 직접 나눠 주는데, 둘 다 같은 앱이라 결과가 같아요. 시험해 보니 두 경우 모두 롤링 배포 중 실패 0건이었어요.

### 우리 Nginx 설정에서 새로 보는 줄

설정 파일은 `deploy.sh`가 서버의 `~/creat-blog/lb/default.conf`에 만들어요 (예시: [`app/deploy/nginx-lb.conf.example`](../../app/deploy/nginx-lb.conf.example)). 2장 설정에 더한 것만 적었어요.

| 설정 | 쉬운 말 |
|---|---|
| `proxy_set_header Host $host` | 학교 Nginx가 넘겨준 도메인(creat.java21.net)을 그대로 앱에 전해요 |
| `X-Forwarded-Proto` (map) | 손님이 https로 왔다는 표시를 학교 Nginx에게 받아 그대로 넘겨요. 이게 있어야 앱이 구글·네이버·카카오에 `https://creat.java21.net/login/oauth2/code/...`로 돌아오라고 알려요 |
| `X-Forwarded-For`, `X-Real-IP` | 손님 IP를 이어 붙여 넘겨요. 앱은 맨 끝의 서버 안 주소(127.0.0.1)들을 건너뛰고 진짜 손님 IP를 써요 (IP별 요청 제한) |
| `client_max_body_size 20m` | 사진 올리기(한 번에 10MB)보다 넉넉하게 |
| `proxy_buffer_size 16k` | 로그인 쿠키·보안 헤더가 많은 응답도 잘리지 않게 |
| `non_idempotent`는 **안 넣음** | 앱에 이미 보낸 글 저장(POST)은 다른 앱에 **다시 보내지 않아요.** 같은 글이 두 번 저장되지 않게요. 내려가는 앱은 새 연결을 아예 안 받기 때문에(연결 거절 = 아직 안 보낸 요청) 그런 POST는 다른 앱으로 안전하게 넘어가요 |
| upstream `keepalive`도 **안 넣음** | 요청마다 새로 연결해요. 쥐고 있던 연결로 보낸 POST가 앱이 꺼지는 순간 실패하는 일을 막아요 |

## 8. 배포할 때 `deploy.sh`가 하는 일

깃허브 `main`에 올리면 Actions가 이미지를 만들어 서버에서 `deploy.sh`를 돌려요. 사람이 할 일은 없어요.

**보통 배포 (두 번째부터)**

| 단계 | 8340 우리 Nginx | 8341 app-a | 8342 app-b | 손님 |
|---|---|---|---|---|
| ① b 교체 | 켜짐 | **혼자 다 받음** | 받던 요청 마치고 내려감 → 새 버전으로 켜짐 | 200 |
| ② `/api/health` 200 확인 + **10초** 대기 | 켜짐 | 받는 중 | 켜짐 (새 버전) | 200 · 다시 번갈아 |
| ③ a 교체 | 켜짐 | 받던 요청 마치고 내려감 → 새 버전 | **혼자 다 받음** | 200 |
| ④ 우리 Nginx 설정이 바뀌었으면 `nginx -t` 검사 뒤 reload | 켜짐 | 켜짐 | 켜짐 | 200 |

- 10초는 우리 Nginx의 `fail_timeout`(5초)보다 길게 잡은 거예요 (5장에서 겪은 502를 피하려고). `SETTLE_SECONDS`로 바꿀 수 있어요.
- 앱을 끌 때는 `docker stop -t 30`이에요. 앱은 받은 요청(글 저장·사진 올리기)을 최대 20초 동안 끝까지 처리하고 내려가요(`server.shutdown=graceful`). 30초가 20초보다 길어서 처리 중인 요청이 잘리지 않아요.
- **새 버전이 안 뜨면**: 그 자리를 바로 전 컨테이너로 다시 켜고 멈춰요. 다른 한 대는 그동안 계속 손님을 받아요. a에서 실패하면 b도 전 버전으로 돌려서 두 대가 같은 버전이 되게 해요.
- 중간에 끊겨 이상한 모양으로 남아도(예: 한 대가 꺼져 있음) 다음 배포가 알아서 정리해요. 꺼져 있는 쪽을 먼저 바꿔요.

**처음 한 번 (지금 서버 → 새 구조로 옮기기)**

지금 서버에는 `creat-blog`(8340), 손으로 띄운 `creat-blog-2`(8341), 시험용 `lbtest`(8342)가 있어요.

1. `lbtest`를 지워요 (8342를 비우려고).
2. 새 버전 app-b를 8342에 띄우고 준비될 때까지 기다려요. 손님은 계속 `creat-blog`(8340)가 받아요.
3. `creat-blog-2`(8341)를 끄고 그 자리에 새 버전 app-a를 띄워요. 이것도 손님과 상관없어요.
4. 빈 호수 8349에 같은 설정으로 시험용 Nginx를 띄워 6번 물어봐요. 8341·8342에 번갈아 가고 모두 200이어야 다음으로 가요. 시험용은 바로 지워요.
5. 12초 기다린 뒤 `creat-blog`(8340)에 종료 신호를 보내고, 8340이 비자마자 우리 Nginx를 켜요. **여기서만 잠깐(시험에서 약 0.3초) 끊겨요.**
6. 8340으로 다시 물어봐서 200이면 `creat-blog`, `creat-blog-2`를 지워요. 끝.

- 1~4 중 어디서 실패해도 `creat-blog`(8340)는 그대로 손님을 받아요.
- 5에서 우리 Nginx가 안 뜨면 우리 Nginx를 지우고 `creat-blog`를 다시 켜요. 이 경우는 앱이 다시 뜨는 동안(15~25초) 끊기지만, 같은 설정을 4에서 미리 시험했기 때문에 거의 일어나지 않아요.

## 용어 한 줄 정리

- **포트**: 한 서버 안에서 프로그램을 구분하는 번호(호수)
- **Nginx**: 앞에서 요청을 받아 뒤의 앱에 넘겨 주는 안내 데스크
- **리버스 프록시**: 손님 대신 뒤의 서버에 다녀오는 것
- **로드 밸런싱**: 여러 앱에 요청을 나눠 주는 것
- **upstream**: Nginx가 요청을 넘길 앱 명단
- **라운드 로빈**: 1번, 2번, 1번, 2번… 돌아가며 주는 방식
- **이중화**: 같은 앱을 두 대 이상 두어 한 대가 죽어도 서비스가 살아 있게 하는 것
- **무중단 배포**: 새 버전으로 바꾸는 동안에도 사이트가 끊기지 않게 하는 배포
- **롤링 배포**: 한 대씩 차례로 새 버전으로 바꾸는 무중단 배포
- **502 Bad Gateway**: Nginx가 뒤의 앱에게 넘기지 못했을 때 내는 에러
- **reload**: Nginx가 바뀐 설정 파일을 끊김 없이 다시 읽게 하는 것
- **graceful shutdown**: 꺼질 때 새 손님은 안 받고, 받은 일은 끝까지 하고 꺼지는 것
- **헬스 체크 (`/api/health`)**: "일할 준비 됐어?"라고 묻는 주소
